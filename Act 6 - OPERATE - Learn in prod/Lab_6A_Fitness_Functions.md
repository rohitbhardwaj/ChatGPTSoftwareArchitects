# Lab 6A — ADRs Converted to Fitness Functions

**Context:** Black Friday incident — 12x traffic, search P95 1.8s, inventory 8 min stale, payment timeouts rising, agent tool retries spiking. Table below converts the governing ADRs and CLAUDE.md rules into measurable, checkable controls.

**Grounding:** Evidence is drawn from `02_Drift_Repo/adrs/*`, `02_Drift_Repo/CLAUDE.md`, the drift repo source (`src/checkoutController.js`, `src/orderService.js`, `src/paymentService.js`, `tests/order.test.js`), and the incident signal table. Where the drift repo already contains code that *fails* the fitness function, that's called out explicitly — it means these controls would have caught the incident's contributing defects before Black Friday, had they existed as CI/runtime gates.

| ADR / Rule | Fitness Function | Check Type | Evidence | Failure Action | Severity | Owner |
|---|---|---|---|---|---|---|
| **ADR-001** Hybrid search | When reranker P95 latency or error rate exceeds threshold, search automatically falls back to BM25 + vector retrieval and continues serving results (no full search failure); overall search P95 stays within SLO even in fallback mode. | Integration (fallback-path test with reranker forced to fail/slow) + Runtime (P95 latency + fallback-invocation-count dashboard/alert) | Incident signal: search P95 = 1.8s during the surge. No reranker/fallback implementation exists anywhere in this repo to inspect statically — ADR-001's operating rule ("fall back to BM25 + vector rather than failing the user journey") is currently undemonstrated in code, so there is no evidence the fallback path was ever exercised or even built. | Auto-trip a feature flag forcing BM25+vector-only mode when reranker latency/error threshold is breached; page search on-call if P95 stays above SLO for >5 min after fallback should have engaged. | High | Search/Platform team |
| **ADR-002** PostgreSQL is authoritative for orders | Every order-status write and every order-recovery read resolves against PostgreSQL; Redis may only be a bounded-staleness read-through cache, never the sole write or read target for recovery, payment, or fulfillment state. | Static (dependency/lint rule banning cache-only writes in order-state methods) + Contract test (`recoverOrder` must read from DB) + CI | `orderService.js:9` — `updateOrderStatus` writes **only** to Redis (`this.redisClient.set(...)`), never touches `this.db`. `orderService.js:14` — `recoverOrder` reads **only** from Redis, with no Postgres fallback. Both directly violate ADR-002. The existing test (`tests/order.test.js:2-4`) is a placeholder (`expect(true).toBe(true)`) that, per its own comment, "protects the wrong Redis-as-truth behavior" — it would not catch this. | Block merge/deploy via CI static+contract gate. In production: alert and run automatic Redis/Postgres reconciliation if the two diverge; treat any Redis-only order-status write reaching prod as a Sev-1 data-integrity bug. | Critical | Order/Platform (backend) team |
| **CLAUDE.md:** domain does not depend on infrastructure | Controllers contain no pricing/domain calculation (HTTP mapping only); domain/service classes may receive infrastructure clients via constructor injection but must not let a cache client silently stand in for the durable store in the same code path. | Static (architecture-boundary linter, e.g. dependency-cruiser / import-boundary ESLint rule across `src/controllers` vs `src/services`) + CI | `checkoutController.js:4-6` — subtotal and `BLACKFRIDAY` coupon discount (`subtotal * 0.70`) are computed directly in the controller, violating "Controllers must not contain pricing or domain rules." `orderService.js` does use constructor-injected `db`/`redisClient` (good DI shape) but then bypasses `db` entirely for authoritative writes (see ADR-002 row) — so the boundary rule is violated in spirit even where DI is nominally present. | Fail CI when a controller file matches a pricing/discount-calculation pattern, or when a domain class writes order/payment state to a cache client without a corresponding durable-store write in the same method. | High | Architecture guild (CODEOWNERS on `src/controllers`, `src/services`) |
| **Security:** no PII in logs | No log statement emits email, physical address, phone, card number, or payment token; logs carry only non-identifying metadata (ids, counts, amounts, statuses). | Static (regex/AST scan for known PII field names passed into `console.log`/logger calls) + CI, backed by Runtime (log-pipeline DLP scanner as defense in depth) | `checkoutController.js:8` — `console.log('checkout request', req.body.customerEmail, req.body.address)` logs email and address in plaintext, exactly the drift flagged in its own inline comment and forbidden by `CLAUDE.md`'s "Do not log PII, tokens, or payment identifiers." | Block merge (CI static scan fails build) on any match. In production, any PII reaching the log sink triggers an immediate security-incident review (redaction, exposure assessment, possible customer notification). | Critical | Security/AppSec team + service owner |
| **CLAUDE.md:** payment requests must be idempotent | Every charge call passes a stable idempotency key (e.g., derived from `orderId` + attempt scope) to the payment provider; a retry reuses the same key so it can never produce a second charge for the same attempt. | Contract/Unit test (mock provider asserts an idempotency key is present and stable across retries) + Runtime (duplicate-charge-per-orderId metric/alert) + **Human Gate** for any change to retry logic | `paymentService.js:6-11` — a 3-attempt retry loop calls `this.provider.charge({ orderId, amount, cardToken })` (`paymentService.js:9`) with **no idempotency key** on any attempt. This is the exact mechanism that turns "payment timeouts increase" (incident signal) into double charges: a timeout doesn't mean the first attempt failed at the provider, and retrying without a key can re-execute it. Directly violates `CLAUDE.md`'s "Payment operations must be idempotent." | CI contract test blocks deploy if no idempotency key is forwarded. In production: circuit-break retries and page payment on-call on any duplicate-settlement signal. Per `CLAUDE.md`, "Payment retry behavior requires plan-first review and payment-owner approval" — so any fix to this file is itself gated on human sign-off before merge, not just automated checks. | Critical | Payments team (payment-owner approval required) |

## Notes
- A fitness function must be measurable — every row above ties to either a static/CI check that can fail a build, a test that can fail before deploy, or a runtime metric with a defined alert threshold.
- Static/CI checks are preferred where possible (rows 2–5 all have code-level evidence today, meaning a CI gate would have caught them before this ever reached production).
- ADR-001 is the one row where no implementation exists to statically check yet — until the reranker/fallback code exists, the control is runtime-only (SLO + fallback-invocation telemetry) and should convert to a static/contract check once that code lands.
- Four of five rows (ADR-002, domain/infra boundary, PII logging, payment idempotency) are **currently failing** in `02_Drift_Repo` — these fitness functions would have flagged real, present defects, not hypothetical ones. Worth carrying that finding into Lab 6C's drift assessment rather than re-discovering it there.
