# Lab 6B — Operating Dashboard Design

**Context:** Same Black Friday incident (12x traffic, search P95 1.8s, inventory 8 min stale, payment timeouts rising, agent tool retries spiking). Each metric below is chosen to answer one question: is the system healthy, *and* is the specific architecture decision behind it (ADR-001, ADR-002, CLAUDE.md rules) actually holding under real load — not just "is the box green."

| Layer | Metric | Target / Alert | Architecture question answered | Owner |
|---|---|---|---|---|
| **User experience** | Search P95/P99 end-to-end latency (incl. reranker) | Target P95 < 500ms (peak-adjusted ≤800ms during declared events); alert if P95 > 1s for 5 min | Is the user actually experiencing the fast hybrid-search path ADR-001 promised, or the degraded/overloaded one? | Search/Platform |
| **User experience** | Checkout completion rate (order confirmed / checkout started) | Target: within 2% of pre-event baseline; alert on drop > 5% | Is the checkout path (controller + service + payment) still functionally sound under load? | Checkout/Order team |
| **User experience** | Checkout error rate (4xx/5xx per attempt) | Target < 1%; alert > 2% | Are user-facing failures rising as a symptom of backend drift? | Checkout/Order team |
| **Platform/SRE** | Reranker P95/error rate + BM25+vector fallback-invocation rate | Target: fallback engages automatically once reranker P95/error crosses threshold; alert if reranker is degraded **but fallback is not firing** (silent failure) | Is ADR-001's fallback mechanism actually engaging, or failing silently while users eat full latency? | Search/Platform |
| **Platform/SRE** | Inventory freshness (time since last successful sync/replication lag) | Target < 60s; alert > 2 min (incident value: 8 min — already past alert) | Is the inventory pipeline keeping pace with 12x traffic, or falling behind in a way that risks overselling? | Inventory/Platform |
| **Platform/SRE** | Redis vs Postgres order-state divergence count | Target 0; alert on any nonzero reading | Is Redis staying cache-only per ADR-002, or has it silently become the write path (as seen in `orderService.js:9,14`)? | Order/Platform |
| **Platform/SRE** | Core service saturation (DB pool utilization, queue depth, CPU/mem on search + checkout + payment services) | Target < 80%; alert > 90% | Are the capacity/backpressure assumptions behind the architecture still valid at 12x forecast? | SRE |
| **AI agent** | Tool-call retry rate (retries per session, per tool) | Target < 5% of calls; alert on spike vs. rolling baseline | Is the shopping agent retrying tools it should instead be backing off from, and is that retry storm self-inflicted load? | AI Platform/Agent team |
| **AI agent** | Tool-call error rate by tool (payment, inventory, search) | Target < 1%; alert > 5% | Which downstream dependency is actually failing under the agent's load, vs. just "agent is misbehaving"? | AI Platform/Agent team |
| **AI agent** | Blocked/attempted actions outside approved scope (DENY-classified actions attempted; ASK-gated actions bypassed) | Target: 0 executed DENY actions; alert on any occurrence | Is agent autonomy staying inside the blast radius approved in Act 5's permission model, even under incident pressure? | AI Platform/Agent team |
| **AI agent** | Agent-triggered payment retries reaching a non-idempotent charge path | Target 0; alert > 0 | Is the agent's retry behavior the mechanism turning payment timeouts into duplicate charges? | AI Platform + Payments |
| **Architecture validity** | Payment idempotency-key presence rate on charge calls | Target 100%; alert on any call below 100% (drift repo today: 0%) | Is CLAUDE.md's "payment operations must be idempotent" rule true in production right now, not just on paper? | Payments |
| **Architecture validity** | ADR-002 violations detected in traffic (authoritative reads/writes hitting Redis only) | Target 0; alert > 0 | Is the "Postgres is authoritative" decision actually enforced at runtime, or only in the ADR document? | Order/Platform |
| **Architecture validity** | PII-in-log scanner hits (real-time DLP match rate on log stream) | Target 0; alert > 0 | Is the "no PII in logs" security rule holding under the log volume of a 12x traffic event? | Security/AppSec |
| **Architecture validity** | Fitness-function CI gate pass rate on merged PRs touching controllers/services/payment | Target 100% | Are the Lab 6A fitness functions actually gating changes, or are violations still merging? | Architecture guild |
| **Business outcome** | Revenue per minute vs. forecast | Target: track within tolerance of 12x forecast plan; alert on shortfall > threshold | Is the architecture's behavior under load costing the business revenue in real time? | Business/Commerce ops |
| **Business outcome** | Duplicate-charge count and dollar exposure | Target 0; alert > 0 | Is the payment-idempotency gap translating into real customer harm and refund/chargeback cost? | Payments + Finance |
| **Business outcome** | Support tickets tagged "stale inventory," "double charge," "search broken" | Target: near baseline volume; alert on spike | Are the technical drift signals actually reaching customers and generating trust damage? | Customer Ops |

## Design notes
- Every row is paired to a concrete, currently-known failure mode from this incident or from the Lab 6A fitness-function findings — nothing here is a generic "system health" metric with no architecture tie-back.
- **Platform/SRE** and **Architecture validity** overlap deliberately (e.g., Redis/Postgres divergence, reranker fallback) but ask different questions: SRE asks "is it degrading," Architecture validity asks "is the *decision* still true." Keeping both prevents an SRE dashboard that's green while the underlying ADR is silently violated.
- The **AI agent** layer is new relative to a traditional ops dashboard — it exists because agent retry behavior is a first-class incident driver here (tool retries spiking → amplifying payment timeouts), so it needs its own blast-radius and retry telemetry rather than being folded into generic platform metrics.
- Alert thresholds are starting points for the workshop, not tuned SLOs — in a real rollout these would be calibrated against pre-event baselines and revisited after this incident's postmortem.
