# Lab 6C — Architecture Drift Assessment

**Analysis only. No files in `02_Drift_Repo` were modified.**

Compared: `02_Drift_Repo/src/checkoutController.js`, `src/orderService.js`, `src/paymentService.js`, `tests/order.test.js` against `adrs/ADR-001-hybrid-search.md`, `adrs/ADR-002-order-state.md`, and `CLAUDE.md`.

**Scope note:** ADR-001 (hybrid search) could not be evaluated — no search, retrieval, or reranker code exists anywhere in this repository to compare against it. That's a coverage gap in the drift repo itself, not a pass/fail on the ADR, and is called out rather than skipped silently.

| Drift Finding | Evidence | Violated Rule / ADR | Severity | Operational Risk | Recommendation |
|---|---|---|---|---|---|
| **1. Redis is being used as the source of truth for order status**, not a cache | `orderService.js:9` — `updateOrderStatus` writes only to `this.redisClient.set(...)`, never to `this.db`. `orderService.js:14` — `recoverOrder` reads only from Redis, with no Postgres fallback. | ADR-002 ("PostgreSQL is authoritative... Redis may cache order views but must never become the source of truth for order recovery, payment state, or fulfillment state") + `CLAUDE.md` ("Redis is cache-only and must not be authoritative for order or payment state") | **Critical** | Redis is not durable by default — an eviction, restart, or memory-pressure event (more likely at 12x Black Friday traffic) can silently lose order status with no durable record to recover from. Risk of unrecoverable orders, double fulfillment, or payment/fulfillment state desync. | **Fix code** (write-of-record moves to Postgres; Redis becomes a cache populated after the DB write; `recoverOrder` reads DB, with Redis only as a fast-path) + **Add test** (replace the placeholder — see finding 5) + **Add CI gate** (static rule: order-state write/read methods must touch the DB, not only the cache client) |
| **2. Pricing and discount logic lives in the controller**, not the domain/service layer | `checkoutController.js:3-6` — subtotal is computed and the `BLACKFRIDAY` coupon applies a 30% discount (`subtotal * 0.70`) directly inside the HTTP handler. | `CLAUDE.md` ("Controllers must not contain pricing or domain rules") | **High** | No single, testable place owns discount rules — any second entry point (an agent-driven checkout path, a batch reprocessing job) can compute totals differently. Also makes it harder to add coupon-abuse/max-discount guards under a promo surge, since the logic isn't centralized where such guards belong. | **Fix code** (move pricing/discount calculation into an order/pricing domain function) + **Add test** (unit tests for discount calculation, currently untested) |
| **3. Customer PII is logged in plaintext** | `checkoutController.js:8` — `console.log('checkout request', req.body.customerEmail, req.body.address)` | `CLAUDE.md` Security section ("Do not log PII, tokens, or payment identifiers") | **Critical** | Direct privacy/compliance exposure. Log storage/aggregation typically has broader access and longer retention than production databases, widening the blast radius of any log-access incident — and at 12x traffic this generates proportionally more exposed PII records during exactly the week logs get pulled most for debugging. | **Fix code** (drop PII fields from the log call; log order/session id instead) + **Add CI gate** (static scan blocking known-PII field names passed to log calls) |
| **4. Payment retries carry no idempotency key** | `paymentService.js:6-11` — a 3-attempt retry loop calls `this.provider.charge({ orderId, amount, cardToken })` (`paymentService.js:9`) with no idempotency key on any attempt. | `CLAUDE.md` Payment section ("Payment operations must be idempotent") | **Critical** | This is the direct mechanism behind the incident's "payment timeouts increase" symptom turning into duplicate charges: a timeout does not mean the provider didn't process the first attempt, so retrying without a key can double-charge — at the highest-volume, highest-timeout moment of the year. | **Fix code** (derive and forward a stable idempotency key per order/attempt) + **Add test** (contract test asserting the key is present and stable across retries) — but per `CLAUDE.md` ("Payment retry behavior requires plan-first review and payment-owner approval"), this fix additionally requires a **human approval gate** before merge, not an autonomous code fix alone |
| **5. The only order-state test is a placeholder that certifies the wrong behavior** | `tests/order.test.js:1-4` — `expect(true).toBe(true)`, with its own comment: "test now protects the wrong Redis-as-truth behavior." | No specific ADR line, but this is the test-coverage gap that let finding 1 ship undetected — a governance/process gap, not a rule violation per se | **High** | Zero regression protection on the most severe finding in this set. Any future change — including an AI-agent-authored refactor — gets no signal that Redis-as-truth is wrong, so the defect is invisible to CI and likely to resurface even after a manual fix. | **Add test** (replace the placeholder with a real contract test: order recovery must reflect Postgres state even when Redis is empty, stale, or unreachable) — this is the necessary companion to fixing finding 1, not a standalone action |

## Required conclusion

- **Fix code:** findings 1, 2, 3, 4 (all four are concrete, located violations — not ADR disagreements)
- **Update ADR:** none — every violation found contradicts an existing, still-valid ADR/CLAUDE.md rule; nothing here suggests the *decision* was wrong, only that the *implementation* drifted from it
- **Add test:** findings 1 (paired with its fix), 2, 4, 5
- **Add CI gate:** findings 1 (order-state DB-touch rule), 3 (PII-log scanner) — both map directly to the fitness functions defined in Lab 6A
- **Add CLAUDE.md rule:** none needed — every violation is already covered by an existing rule; the gap is enforcement, not policy. (The one true gap — ADR-001 having no implementation to check — isn't a CLAUDE.md gap either; it's a "build the fallback path, then add the check" item.)

**Overall read:** this is not an ADR problem, it's an enforcement problem. All four code-level violations were already forbidden by name in `CLAUDE.md` before this code was written — none of them are new judgment calls. The fastest durable fix is exactly what Lab 6A proposed: turn these five rows into CI/runtime gates so the same drift can't merge silently a second time. No files were changed to produce this assessment; fixes should go through the same governed-PR / ARCH-GATE review process used in Act 5 before merge, with finding 4 additionally requiring payment-owner sign-off per `CLAUDE.md`.
