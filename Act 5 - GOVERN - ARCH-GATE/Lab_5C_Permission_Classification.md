# Lab 5C — Permission Classification

Classified using blast radius, reversibility, data sensitivity, production impact, and audit needs — consistent with the ShopSmart rules established across the workshop (no new dependency without approval; payment, auth, schema, public API, and production-impacting changes require explicit human approval; never expose secrets/PII).

Framework used for the three buckets:
- **ALLOW** — low blast radius, reversible, no sensitive data, no production impact. Safe to run autonomously; still logged for audit, but no human gate needed per instance.
- **ASK** — legitimate, expected part of the workflow, but with enough blast radius / irreversibility / production exposure that a human must approve *this specific instance* before the agent proceeds.
- **DENY** — the agent should not perform this action at all, categorically, even with a human "yes" click — either because the correct actor is a human or a separately-gated pipeline, or because the action is inherently destructive/irreversible/secret-exposing in a way that shouldn't be delegated through a simple approval prompt.

| Agent action | ALLOW | ASK | DENY | Reason |
|---|---|---|---|---|
| Read source files | X | | | Read-only, zero blast radius, trivially reversible (no state change at all), no sensitive data, no production impact. Baseline action every other decision in this table builds on. |
| Run unit tests | X | | | Executes in a sandboxed/dev context, no persistent state change beyond test artifacts, fully reversible, no production impact. Assumes tests don't run against production data — if they did, this row would move to ASK. |
| Run formatter | X | | | Mechanical, deterministic, no semantic change. Modifies files but the diff is trivially reviewable and revertible via git; no data sensitivity, no production impact. The resulting change still goes through normal PR review before merge — that's a separate gate, not part of this action. |
| Install dependency | | X | | Matches the workshop's standing rule: "no new dependency without approval." Blast radius includes supply-chain risk (a package can run arbitrary code at install time via postinstall scripts) and affects the whole build; reversible in principle but not in effect once installed and executed. Legitimate, routine engineering need — so ASK, not DENY — but never autonomous. |
| Run database migration | | X | | Schema changes are explicitly named as approval-required across this workshop's CLAUDE.md rules. Assumes a reviewed, tested migration executed through the standard controlled pipeline (not ad hoc SQL run directly against a live database) — under that assumption it's a legitimate, human-approved workflow step. If this were an untested migration run directly against production, it would push toward DENY instead. |
| Read .env | | | X | Highest data sensitivity in the table — raw credentials, API keys, tokens. Even a read-only access puts secrets into the agent's context, creating exfiltration/leak risk in any later output or log. The agent should never read raw secret files; a scoped, audited secrets-manager abstraction (e.g., "does this key exist," not "what is its value") replaces this need. |
| Print environment variables | | | X | Same sensitivity as reading `.env`, but worse in effect — this actively pushes secret values into a transcript, log, or terminal output that may be captured, retained, or shared. Directly violates the standing "never log secrets/tokens" rule. |
| Create PR | X | | | Visible and reversible (can be closed without effect), makes no changes to the deployed system, and is itself the audit record. This is the *correct* mechanism for an agent to propose anything risky — it creates the review gate rather than bypassing it, which is why it's ALLOW even for changes whose actual merge would be ASK/DENY. |
| Change authentication logic | | X | | Security-critical, high blast radius, and explicitly named as approval-required. Classified ASK rather than DENY because drafting/proposing an auth change is legitimate engineering work — but this is the strictest form of ASK in the table: it requires a **named security/auth owner** to review line-by-line, not a generic one-click confirmation, and the agent should never merge or deploy this itself regardless of who approved the draft. |
| Deploy to production | | | X | Maximum blast radius (all live customers, simultaneously), imperfectly reversible (rollback is possible but carries downtime/data-consistency risk), and explicitly named as approval-required. The agent's role stops at preparing/tagging a release candidate (e.g., via a PR or release branch) — the actual deploy trigger belongs to a human or a separately human-gated CI/CD pipeline, never the agent directly, even with a prior "yes." |
| Delete data/table | | | X | Potentially catastrophic and irreversible (data loss if no verified backup, cascading effects if referenced elsewhere). This class of destructive action shouldn't be delegated through a simple approval prompt at all — it needs a formal, out-of-band change process (backup verification, staged/soft delete, second approver) that sits outside the agent's action space entirely. |
