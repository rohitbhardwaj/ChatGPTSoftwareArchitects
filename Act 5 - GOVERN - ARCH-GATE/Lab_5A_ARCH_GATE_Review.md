## Gate Decision

**Split PR.**

- **Approve as-is:** the layering fix (controller → service) and the log redaction. These have zero behavior change, are exactly what CLAUDE.md asks for, and close the PII/token logging smell called out since Act 4.
- **Hold for explicit approval:** the discount-code strict-validation behavior (`orderService.js:19`, `orderController.js:8` interaction). This is a public API contract change (new 400 failure mode for previously-succeeding requests) and per the stated rule set, "public API... changes require explicit human approval" — none is on record here. A human owner needs to decide: (a) approve the stricter behavior and treat it as an intentional, documented breaking change, or (b) revert to silently ignoring unknown discount codes to preserve current contract, or (c) accept the throw but change the resulting status/response so it's clearly a new, versioned behavior.

Not a flat **Reject** — most of the diff is a clean, low-risk architecture fix worth keeping now. Not a plain **Approve** — merging as one PR would ship an unreviewed API break under cover of a "safe refactor" label.

## Required Follow-up
1. Get explicit sign-off on the discount-code validation behavior change, or revert that one `throw` and cover it with a characterization test instead (gate C).
2. Add `console.error(err)` (or structured equivalent) in the controller's catch block before responding, so failures stay visible in logs (gate T).
3. Add tests for: `orderController.js`'s 201/400 mapping, inventory-unavailable path, and payment-charge-failure path (gate A).
4. Consider differentiating HTTP status by error type (e.g., 409 for inventory conflict) instead of collapsing every thrown error to 400 (gates C/G).
