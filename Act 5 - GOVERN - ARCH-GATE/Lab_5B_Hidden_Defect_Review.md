# Lab 5B — Hidden Defect Review

Each defect below is mapped to the ARCH-GATE dimension(s) it violates (A-Architecture fit, R-Risk & rollback, C-Correctness, H-Hidden coupling, G-Guardrails & security, A-Automated tests, T-Traceability, E-Evolution), the operational risk it creates, and the smallest safe fix. Where a concrete instance of the defect exists in repos already reviewed this workshop (Act 6 drift repo, Act 4/5 PR), it's cited directly as evidence rather than treated only as a hypothetical pattern.

| Hidden defect | Likely violation | Operational risk | Recommended action |
|---|---|---|---|
| **Controller calls database directly** | **A — Architecture fit**: breaks the layered contract (controller → service → repository) every CLAUDE.md in this workshop states explicitly. **H — Hidden coupling**: the controller now depends on persistence/schema details directly, and bypasses whatever validation and business rules live in the service layer for that same operation. **E — Evolution**: harder to swap persistence, add caching, or centralize cross-cutting concerns once DB access is scattered across controllers. | Business rules the service layer is supposed to enforce (pricing checks, quantity validation, idempotency) can be silently bypassed through this second path into the data, since it never runs through the service. Schema changes gain a wider, less predictable blast radius because more than one layer now touches the DB shape directly. | Extract the direct call into the corresponding service method; have the controller call the service instead of the DB. Add a static architecture-boundary rule (e.g., a dependency-cruiser/ESLint import rule forbidding `src/controllers/**` from importing any DB/repository/ORM module) so this can't reappear silently in a future PR. |
| **Payment retry without idempotency** | **G — Guardrails & security**: violates the standing payment rule ("payment operations must be idempotent"). **C — Correctness**: retry-without-idempotency can produce a different real-world outcome (a second charge) than the single-charge contract the API implies. **R — Risk & rollback**: unlike a bad deploy, a duplicate charge isn't cleanly reversible — refunding it has real customer and trust cost. | Directly observed in this workshop: `Act 6 - OPERATE - Learn in prod/02_Drift_Repo/src/paymentService.js:9` retries `provider.charge()` up to 3 times with no idempotency key. A timeout does not prove the provider failed to process the first attempt, so retrying blind risks double-charging — and the risk scales with retry volume, i.e. worst exactly when timeouts spike under peak load. | Add a stable idempotency key (derived from `orderId` + attempt scope) to every charge call and forward it to the provider. Add a contract test asserting the same key is reused across retries. Per CLAUDE.md, payment retry-behavior changes also require **payment-owner sign-off** before merge — this is a human gate, not just an automated fix. |
| **Sensitive data appears in logs** | **G — Guardrails & security**: direct violation of "do not log PII, tokens, or payment identifiers." **T — Traceability**: the fix has to walk a line — remove the sensitive fields without losing the ability to correlate the log line to an order/request. | Also directly observed: `Act 6 - OPERATE - Learn in prod/02_Drift_Repo/src/checkoutController.js:8` logs `customerEmail` and `address` in plaintext. Log aggregation systems typically have broader access and longer retention than production databases, so this widens the blast radius of any log-access incident into a privacy/compliance exposure, not just an internal one. | Remove PII fields from the log call; log a non-identifying reference (order id, session id) instead. Add a CI-level static scan that blocks known-PII field names from reaching any logger/`console.*` call, so the defect can't merge again under a different call site. |
| **Tests are weakened to match generated behavior** | **A — Automated tests**: the gate this defect breaks most directly — tests stop proving behavior and start certifying whatever the generator happened to produce. **C — Correctness**: a real regression can hide behind a fully green suite because the assertion was rewritten to match the new output instead of the intended contract. **R — Risk & rollback**: this is the most dangerous shape of "the PR looks safe," because it manufactures false rollback/merge confidence — the safety net was edited, not the code alone. | Illustrated by the Act 4 PR reviewed in Lab 5A: it changed discount-code handling from "unknown codes silently ignored" to "unknown codes throw a 400" — a public API behavior change — and updated the test file alongside it rather than first adding a characterization test of the *prior* behavior. Had that test edit gone one step further (asserting the new, breaking behavior as simply "correct," with no old-behavior test anywhere for comparison), a reviewer glancing at "tests pass" would have no way to notice the regression at all. The operational risk is a real behavior break shipping to production wrapped in a passing suite — worse than no tests, because it creates confidence that isn't earned. | Treat any **changed assertion** (not just a newly added one) as requiring explicit justification in the PR description against the ADR/CLAUDE.md/prior behavior. Enforce CLAUDE.md's existing rule — "add characterization tests before refactoring behavior" — as a checklist/gate item: a test-file diff that changes an existing expected value needs a paired characterization test proving what the *old* behavior was, plus explicit reviewer sign-off, before it can merge. |
